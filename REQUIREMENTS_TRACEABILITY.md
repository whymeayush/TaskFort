# Newtonite Software Engineering Challenge - Requirement Traceability Matrix (RTM)

| Req ID | Source Page | Requirement Description | Planned Module / Component | Verification Method | Assumptions & Architectural Notes |
|---|---|---|---|---|---|
| **REQ-1.1** | Page 1 | Understand problem, make reasonable assumptions, take system ownership | System Design, Architecture Docs & `ENGINEERING_DECISIONS.md` | Code review, Documentation Audit | Fast-growing mid-market ops environment with diverse operational request types. |
| **REQ-2.1** | Page 2 | Work items representing 6 core types (Customer Issue, Engineering Problem, Payment Investigation, Production Incident, Compliance Request, Operational Approval) | Data Model (`work_items` table schema, type enum, metadata schemas) | Unit tests (`schema.test.ts`), DB migrations | Specific metadata fields can vary by type (e.g. payment amount, incident severity, regulatory deadline). |
| **REQ-2.2** | Page 2 | Understand what the item is and why it exists | Work item summary, description, context tags, business impact fields | UI Inspection, API response validation | Every work item requires a title, description, and categorized reason/impact. |
| **REQ-2.3** | Page 2 | Current state and importance (Priority & Urgency) | Status enum (`DRAFT`, `TRIAGED`, `IN_INVESTIGATION`, `PENDING_APPROVAL`, `RESOLVED`, `CLOSED`), Priority enum (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`) | State transition validator tests, UI badge verification | High/Critical items trigger automated triage escalations and notifications. |
| **REQ-2.4** | Page 2 | Who is responsible for it (Assignee & Owning Team) | Team membership & assignment engine (`owner_id`, `team_id`) | RBAC unit tests, assignment endpoint tests | An item always belongs to a primary team; assignment can change with recorded provenance. |
| **REQ-2.5** | Page 2 | What has happened previously (Audit trail & history) | Audit Trail Module (`audit_events` table, event logger, chronological timeline component) | Integration tests on state mutation verifying immutable audit records | Audit events are append-only; changes record actor, timestamp, diff (before/after), and comment. |
| **REQ-2.6** | Page 2 | What requires attention next (Blockers & Next actions) | Work Item Attention Engine (`next_action_required`, `pending_approval_role`, SLA timers) | Dashboard attention queue tests, visual indicator checks | Explicit visual cues show who has the blocking action (e.g., "Awaiting Compliance Lead Approval"). |
| **REQ-2.7** | Page 2 | Sensible behavior during concurrent interactions | Optimistic Concurrency Control (OCC) with `version` field + HTTP 409 Conflict | Concurrency integration tests with simultaneous workers | Clients pass `version` in payload or `If-Match`; collisions return server state and trigger conflict resolution. |
| **REQ-3.1** | Page 3 | Multi-team structure with user roles & permissions | RBAC Engine (`users`, `teams`, `user_teams`, roles: `AGENT`, `LEAD`, `ADMIN`) | Auth unit tests for role matrix | Users can belong to multiple teams with distinct roles in each team. |
| **REQ-3.2** | Page 3 | Server-enforced authorization (not just hidden UI controls) | Express Middleware (`authorizeResourceAccess`, `enforceRole`) | Negative security integration tests (403 Forbidden on direct API calls) | Compliance and financial payment items enforce strict team-level confidentiality policies. |
| **REQ-3.3** | Page 3 | Collaboration history & workflow progress without data loss | History Timeline UI, Collaboration Comments with mention/event markers | End-to-end timeline testing | Comments and system events are combined in a unified chronological activity feed. |
| **REQ-3.4a** | Page 3 | Concurrent claim: Two users attempting to take responsibility for same work | Atomic assignment with version lock (`UPDATE work_items SET owner_id = ?, version = version + 1 WHERE id = ? AND version = ?`) | Automated parallel race condition tests (5 concurrent workers trying to claim) | Exactly one claimant succeeds (HTTP 200); subsequent claimants receive HTTP 409 with current owner details. |
| **REQ-3.4b** | Page 3 | Stale information handling: One user viewing info another user just changed | Server-Sent Events (SSE) `/api/events` + client-side stale detection badge | Browser / subagent multi-tab sync test | If client is viewing version N and receives SSE event for version N+1, a "Record updated by another user" toast/banner appears with instant reload action. |
| **REQ-3.4c** | Page 3 | Multiple updates reaching system in short period | Database transactions (SQLite WAL mode + serializable/immediate transactions) | Load/burst concurrency test script | High frequency burst writes maintain monotonic version increments and audit order. |
| **REQ-3.4d** | Page 3 | Accidental duplicate operations from repeated submissions | Idempotency Engine (`idempotency_keys` table + middleware) | Automated retry test with identical `Idempotency-Key` header | Duplicate requests return cached 200/201 response body and code without re-executing business logic or creating duplicate audit entries. |
| **REQ-3.5** | Page 3 | High-efficiency overview of ongoing work & triage | Dashboard "Needs Attention" queue, Quick Filters, Server-side text search | Filter and search query performance tests | Default view shows items requiring action by current user or current user's team. |
| **REQ-3.6** | Page 3 | Usable as stored work grows (Scale UX) | Server-side cursor/offset pagination, SQL indexing on `(team_id, status, updated_at)` | Database benchmark test with 10,000 synthetic records | Browser never loads more than pageSize (e.g. 20-50) records at once. |
| **REQ-3.7** | Page 3 | Secondary asynchronous processing (failure/retry handling) | Transactional Outbox (`outbox_jobs` table) + Asynchronous Worker Process | Worker failure & dead-letter queue test, retry backoff test | Notifications and audit enrichment run via outbox worker; at-least-once delivery with idempotency guards. |
| **REQ-4.1** | Page 4 | Scalable architecture (10k+ items, thousands of users) | SQLite WAL mode (or PostgreSQL-ready schema), indexed queries, paginated endpoints | Query EXPLAIN tests, pagination stress test | In-memory filtering is banned; all search/filter operations use indexed SQL WHERE clauses. |
| **REQ-4.2** | Page 4 | Engineering rigor across full stack | Modular TypeScript/ESM architecture, schema validation, typed API contracts | Automated CI test suite, type checking | Clean separation between Controller, Service, Repository, and Middleware. |
| **REQ-4.3** | Page 4 | At least 3 non-CRUD critical behaviors demonstrated | 1. Optimistic Concurrency Control (OCC)<br>2. Idempotency Key deduplication<br>3. Workflow State Machine rules<br>4. Resource-level RBAC<br>5. Reliable Outbox Worker | Automated tests for all 5 critical behaviors | The system implements all 5 critical patterns rather than just the minimum 3. |
| **REQ-5.1** | Page 5 | `ENGINEERING_DECISIONS.md` documenting ~5 key decisions & tradeoffs | Markdown doc in workspace root | Peer review checklist against criteria | Explicitly explains: DB choice, OCC vs pessimistic locks, Idempotency design, Sync vs Async boundary, RBAC model. |
| **REQ-5.2** | Page 5 | Automated tests for dangerous/critical behaviors | Vitest / Jest test suite (`tests/concurrency.test.ts`, `tests/idempotency.test.ts`, `tests/workflow.test.ts`, `tests/rbac.test.ts`) | Automated test execution (`npm test`) passing 100% | Focus on race conditions, unauthorized state transitions, and duplicate mutations. |
