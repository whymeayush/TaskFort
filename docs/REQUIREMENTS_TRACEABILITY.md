# Requirements Traceability Matrix (RTM) — Newtonite Operations Hub

This document maps all six pages of the **Newtonite Software Engineering Challenge: Operations Under Pressure** candidate brief to the MERN stack architecture, components, database models, and automated tests.

---

| Req ID | Brief Page | Category | Detailed Requirement Description | Implemented Module / File | Model / API / Component | Verification Test Suite | Assumptions & Architectural Notes |
|---|---|---|---|---|---|---|---|
| **REQ-1.1** | Page 1 | Engineering Ownership | Understand operational pressures, make sensible assumptions, design coherent system. | `docs/IMPLEMENTATION_PLAN.md`, `ENGINEERING_DECISIONS.md` | System Architecture | Architectural review, CI test runner | Fast-scaling mid-market enterprise with multiple departments requiring a unified workspace. |
| **REQ-2.1** | Page 2 | Work Item Models | Support 6 core types: Customer Issue, Engineering Problem, Payment Investigation, Production Incident, Compliance Request, Operational Approval. | `server/src/models/WorkItem.js` | `WorkItem` schema enum `['CUSTOMER_ISSUE', 'ENGINEERING_PROBLEM', 'PAYMENT_INVESTIGATION', 'PRODUCTION_INCIDENT', 'COMPLIANCE_REQUEST', 'OPERATIONAL_APPROVAL']` | `server/tests/workItems.test.js` | Each type contains specific contextual metadata (e.g. payment transaction amounts, incident severities, regulatory deadlines). |
| **REQ-2.2** | Page 2 | Item Purpose | Understand what the item is and why it exists. | `server/src/models/WorkItem.js`, `client/src/pages/WorkItemDetail.jsx` | `WorkItem.reasonForExistence`, `WorkItem.businessImpact` | `server/tests/workItems.test.js` | Every item requires explicit root cause / trigger fields, not just a generic title. |
| **REQ-2.3** | Page 2 | State & Importance | Current state and importance (Priority & Urgency). | `server/src/models/WorkItem.js`, `server/src/services/workflowService.js` | Priority: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`; Status: `Open`, `In Progress`, `Blocked`, `In Review`, `Resolved`, `Closed` | `server/tests/workflow.test.js` | High/Critical items trigger SLA indicators and triage queues. |
| **REQ-2.4** | Page 2 | Ownership & Teams | Who is responsible for it (Assignee & Owning Team). | `server/src/models/WorkItem.js`, `server/src/services/assignmentService.js` | `WorkItem.assigneeId`, `WorkItem.teamId` | `server/tests/assignment.test.js` | Work item is always anchored to an owning team; assignment can change with recorded history. |
| **REQ-2.5** | Page 2 | Prior Activity History | What has happened previously (Audit trail, timeline, history). | `server/src/models/ActivityLog.js`, `server/src/services/auditService.js`, `client/src/components/ActivityTimeline.jsx` | Append-only `ActivityLog` collection (`actorId`, `actionType`, `field`, `prevValue`, `newValue`, `correlationId`) | `server/tests/audit.test.js` | Immutable log; regular users cannot edit or delete audit events. |
| **REQ-2.6** | Page 2 | Next Actions | What requires attention next (Blockers, pending approvals, SLA). | `server/src/models/WorkItem.js`, `client/src/pages/Dashboard.jsx` | `WorkItem.nextActionRequired`, `WorkItem.pendingApprovalRole` | `server/tests/dashboard.test.js` | Attention cards highlight unassigned urgent work and pending approvals. |
| **REQ-2.7** | Page 2 | Sensible Concurrency | System behaves sensibly during concurrent interactions. | `server/src/services/assignmentService.js`, `server/src/models/WorkItem.js` | Optimistic Concurrency Control (OCC) using `version` / `revision` field and atomic conditional queries | `server/tests/concurrency.test.js` | Conflicts return HTTP 409 with server version; frontend allows diff review. |
| **REQ-3.1** | Page 3 | Multi-Team Identity | Users belong to 1+ teams with distinct roles in each team. | `server/src/models/Team.js`, `server/src/models/TeamMembership.js`, `server/src/models/User.js` | `TeamMembership` with roles: `TEAM_ADMIN`, `TEAM_MEMBER`, `READ_ONLY` | `server/tests/rbac.test.js` | Users can hold different responsibilities per team. |
| **REQ-3.2** | Page 3 | Server Authorization | Meaningful authorization enforced server-side, not just UI hiding. | `server/src/middleware/auth.js`, `server/src/middleware/rbac.js` | JWT auth middleware + Resource-Level RBAC checks | `server/tests/rbac.test.js` | Unauthorized direct API calls receive HTTP 403 Forbidden. |
| **REQ-3.3** | Page 3 | Collaboration History | Collaboration around items; important actions do not silently disappear. | `server/src/models/Comment.js`, `server/src/models/ActivityLog.js` | MongoDB transactions committing mutation + activity log atomically | `server/tests/audit.test.js` | Multi-document transactions guarantee state and audit records succeed or fail together. |
| **REQ-3.4a** | Page 3 | Concurrent Claim | Two users attempting to take responsibility for the same work item. | `server/src/services/assignmentService.js` | Atomic conditional assignment (`findOneAndUpdate({ _id, assigneeId: null, version })`) | `server/tests/concurrency.test.js` | Exactly one user succeeds (HTTP 200); the second receives HTTP 409 Conflict. |
| **REQ-3.4b** | Page 3 | Stale Updates | One user viewing information another user just changed. | `server/src/services/workItemService.js`, `client/src/components/ConflictModal.jsx` | Expected version check (`version === expectedVersion`); HTTP 409 on mismatch | `server/tests/concurrency.test.js` | Stale write is rejected with 409; client preserves draft and prompts reconciliation. |
| **REQ-3.4c** | Page 3 | Rapid Updates | Multiple updates reaching the system within a short period. | `server/src/models/WorkItem.js` | Atomic version increments (`$inc: { version: 1 }`) | `server/tests/concurrency.test.js` | High-frequency burst writes maintain monotonic revision sequence. |
| **REQ-3.4d** | Page 3 | Duplicate Requests | User repeating action due to uncertain network/timeout. | `server/src/middleware/idempotency.js`, `server/src/models/IdempotencyKey.js` | `Idempotency-Key` header with cached response replay (`X-Cache: HIT-IDEMPOTENT`) | `server/tests/idempotency.test.js` | Replays return identical status/payload without repeating side effects or audit logs. |
| **REQ-3.5** | Page 3 | Overview & Triage | Overview of ongoing work; quickly determine what requires attention without manual browsing. | `client/src/pages/Dashboard.jsx`, `client/src/pages/AllWorkItems.jsx` | Server-side Attention Queries (`GET /api/dashboard/summary`) | `server/tests/dashboard.test.js` | Summary cards: Attention Queue, Urgent Incidents, Pending Approvals, Overdue Work. |
| **REQ-3.6** | Page 3 | Usability at Scale | System remains responsive as stored work grows. | `server/src/controllers/workItemController.js`, `client/src/components/Pagination.jsx` | Server-side pagination (`skip`/`limit`), compound indexes | `server/tests/pagination.test.js` | Client never loads entire collection into memory; paginated in slices of 15-50. |
| **REQ-3.7** | Page 3 | Secondary Async Work | Actions such as notifications or enrichments happen reliably after primary action. | `server/src/services/notificationService.js`, `server/src/models/Notification.js` | In-app notification dispatcher with deduplication keys and retry handling | `server/tests/notification.test.js` | Failure in notification dispatch does not roll back the primary operational action. |
| **REQ-4.1** | Page 4 | Expected Scale | 10k+ items, thousands of users, many teams; no unbounded client memory scans. | `server/src/models/WorkItem.js` (indexes) | Compound MongoDB indexes: `(teamId, status)`, `(assigneeId, status)`, `(priority, status)` | `server/tests/scale.test.js` | Query projections and indexed filters maintain sub-10ms query execution. |
| **REQ-4.2** | Page 4 | Engineering Rigor | Meaningful consideration of data modeling, API design, state management, RBAC, concurrency, error handling. | Full Stack Monorepo (`server/`, `client/`) | Clean Controller-Service-Repository architecture, Zod validation | CI integration tests | Layered architecture cleanly isolates concerns. |
| **REQ-4.3** | Page 4 | >=3 Critical Non-CRUD Behaviors | Demonstrate correctness beyond simple CRUD. | 1) Atomic OCC Assignment<br>2) Stale-Version Rejection (409)<br>3) Idempotency Key Deduplication<br>4) Multi-document Transactions<br>5) Approval Guardrails | `server/tests/concurrency.test.js`, `server/tests/idempotency.test.js`, `server/tests/workflow.test.js` | Automated concurrency, idempotency, and workflow test suites | All 5 critical non-CRUD scenarios implemented and verified. |
| **REQ-5.1** | Page 5 | Engineering Decisions | Document ~5-8 important decisions, trade-offs, and what was intentionally omitted. | `ENGINEERING_DECISIONS.md` | Markdown documentation in root | Peer review checklist | Detailed analysis of MERN/Mongo, OCC vs locking, Idempotency, RBAC, Sync vs Async. |
| **REQ-5.2** | Page 5 | Automated Testing | Identify high-risk behaviors and write automated tests. | `server/tests/*.test.js`, `client/tests/*.test.jsx` | Vitest / Supertest integration test suite | `npm test` passing 100% | Focus on race conditions, unauthorized mutations, stale overwrites, and retries. |
| **REQ-5.3** | Page 5 | Complete Submission | Working source, run instructions, setup guide, decisions doc, tests, known limitations. | `README.md`, `docs/KNOWN_LIMITATIONS.md`, `package.json` | Running platform | Setup verification | Zero external installation hurdles; runs with Node.js and persistent MongoDB. |
| **REQ-6.1** | Page 6 | Final Discussion Readiness | Demonstrate application, explain failure handling, assumptions, and scaling roadmap. | `docs/DEMO_SCRIPT.md`, `docs/ARCHITECTURE.md` | Interactive UI with multi-user persona switcher | Live demonstration | Pre-seeded with 6 realistic operational scenarios ready for evaluator walk-through. |
